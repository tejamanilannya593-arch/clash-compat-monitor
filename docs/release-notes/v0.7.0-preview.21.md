# ClashCompatibilityMonitor v0.7.0-preview.21

ChatGPT 不可达现在是最高优先级恢复事件。程序不再等待当前节点的第二次复检，而是并发测量全部候选的 Clash 延迟，再对所有 Clash 可达候选并发测量 ChatGPT URL 延迟；随后按 ChatGPT 延迟从低到高执行采用 2 秒单项探针预算的完整复检，首个通过实际出口地区、ChatGPT、Steam API、Google 及全部已选服务的节点立即切换。

恢复扫描不再受普通路径“最多 8 个候选”或“找到 3 个候选即停止”的限制。即使大部分节点不可达，也会以每批最多 12 个完整复检、未遍历完时约 100 ms 后立即续批的方式持续检查所有仍有 Clash 延迟的节点；剩余节点按名称持久化，不会因下一轮延迟重排而跳过。只有完整遍历一遍仍无安全目标时才等待 3 秒重新开始。确认的 ChatGPT 故障继续绕过性能寻优切换预算，避免用户在当前节点已经不可用时进入普通等待。

两轮全节点延迟测量采用最多 64 路并发的连续批处理，每个候选都会获得一次测量；单请求设有更短的管道连接、写入和读取时限。个别 Mihomo 请求超时或返回畸形延迟时只把该项记为未知，不再中止整个恢复周期。

程序仍只操作代理组选择，不修改 Clash 配置或订阅文件。响应过慢和主动性能寻优仍保留原有切换预算及观察、回退规则。
