# 快速且保守的节点质量判断设计

## 目标

把当前节点的一轮服务判断从串行等待改为并发等待，使正常结果在约 3～6 秒内出现；同时用 P75 和最慢服务替代简单平均值，避免“多数服务较快、单项严重卡顿”仍显示为良好。

## 检测流程

- 选定兼容性探测组节点后，并发执行本轮所选服务探测；出口身份检测与服务探测同时开始。
- 所有探测仍各自受 5 秒上限约束，聚合结果时按用户配置中的服务顺序决定首个明确失败，保证结果稳定。
- 当前节点结果一旦完成，界面显示实际状态；备用节点筛选继续后台执行，不把已得到的基础可用状态重新显示成“正在检测”。
- 不改变连续失败确认、30 分钟/5 次/95% 稳定历史要求、切换后回退或地区实测原则。

## 质量口径

- 只统计有有效响应时间的已通过/部分通过服务，按 nearest-rank 计算 P75。
- 等级：P75 ≤300 ms 为“优秀”，≤500 ms 为“良好”，≤800 ms 为“可用但偏慢”，>800 ms 为“较慢”。
- 任一服务 >2000 ms 时，在综合响应中直接指出最慢服务及其延迟。
- 自动性能寻优继续要求当前节点连续三次 P75 >800 ms；候选的五次历史 P75 中位数需 ≤500 ms、单项服务仍需满足原有 1500 ms 安全上限。

## 界面语义

- AI 入口可达但账号/对话未验证时，标题显示“基础连接可用”，服务行继续明确“真实对话待验证”。
- 未取得任何可靠结果才显示“正在检测”或“部分服务待验证”。

## 验证

- 单元测试覆盖并发进入、确定性失败顺序、P75、最慢服务提示和基础可用状态。
- 运行完整构建、增强脚本测试和发布检查。
- 安装后实测当前节点耗时、界面文字、Google/GitHub 连通性，并重启守护程序复验。
